# Design: Consolidate Daily Activity Journal into Zettly

## Intent & Why

Today the "what I / my AI worked on" record lives in `daily-activity-journal`:
a Markdown repo (`activity/ACTIVE.md`, `activity/daily/YYYY/MM/*.md`) plus a
Python hook (`scripts/codex_journal.py`) that captures Codex sessions into a
local SQLite file (`%LOCALAPPDATA%\DailyActivityJournal\events.sqlite3`) and
renders reports to Markdown + a Discord webhook.

That is two parallel record-keeping systems (Markdown repo + SQLite) plus a
manual handoff protocol (Git) across machines. Zettly already has:
- multi-user auth (Sanctum, `/api/v1` CLI tokens)
- `Todo` (task + note), `Habit`, `Focus`, `Drawing`, knowledge graph
- an API surface the Codex hook could write to directly

Factory stays untouched: it is the development-task ledger/runner and does not
need to absorb journal data.

**Goal:** one place (Zettly) for daily activity + agent (Codex) session logs +
reports, replacing the journal's parallel systems. No duplicate sources of
truth.

## Goals

- Codex hook writes agent sessions + events to Zettly (replacing local SQLite).
- Zettly stores: agent sessions, agent events, journal entries (manual),
  reports, report deliveries.
- Reports generated by Zettly (daily/weekly/monthly), delivered to a
  configured webhook (Discord/Telegram) via a queued Laravel job.
- `ACTIVE.md` task list + daily handoff notes become Zettly `Todo` items
  (one door, full consolidation).
- Historical journal data (SQLite + Markdown daily files) is one-time
  migrated into Zettly as seed.

## Non-Goals

- Do not touch Factory.
- Do not rebuild the PocketBase spec (that was the abandoned draft approach;
  we fold the same fields into Zettly instead).
- No mobile/web UI rework required for this; the existing Zettly web app can
  gain a simple "Journal" view later if wanted, but the API + CLI is the
  contract here.
- No cross-machine Git handoff protocol anymore (Zettly is the shared store;
  handoff = read the latest agent session / todo state from Zettly).

## Anti-Goals (what would make this a failure)

- Data existing in two places (SQLite AND Zettly) as live source of truth.
- Reports still generated only on one machine (must be server-side, reachable
  by any machine's hook).
- Losing historical journal records during migration.

## Constraints

- Zettly is Laravel 12, PHP 8.2+, React/Inertia front-end; the new surface is
  primarily API + models + migration + queued job, not new front-end
  complexity.
- The Codex hook is a tiny Python script that runs on every
  `UserPromptSubmit`/`PostToolUse`/`Stop`/`SessionStart` event; it must stay
  fast and resilient (offline-tolerant, retries, no blocking the agent).
- Auth: reuse Zettly Sanctum CLI token (`abilities:zettly:cli`). The hook
  will use a dedicated long-lived CLI token per machine.
- Secrets: keep the existing `SECRET` redaction regex; do not store raw
  credentials in agent events.

## Approaches considered

1. **A. Fold journal into Zettly's own DB (recommended).** New migrations:
   `agent_sessions`, `agent_events`, `journal_entries`, `reports`,
   `report_deliveries`. New API under `/api/v1/...` (same Sanctum CLI
   ability). Codex hook POSTs directly to Zettly. Reports via Laravel queued
   job + webhook. One source of truth, reuses existing auth/queue.
   - Pros: no parallel system, no new infra, reuses what already exists.
   - Cons: adds schema + endpoints to Zettly (fine, additive).
2. **B. PocketBase (the old draft spec).** New dedicated store, Zettly
   proxies. Rejected: duplicate system, spec was never implemented, adds sync
   complexity — exactly the duplication we are trying to remove.
3. **C. Hybrid: keep Markdown as source of truth, Zettly only reads.**
   Rejected: dual-write, conflict resolution is fiddly, and handoff would
   still be Git-based (defeats the point).

**Chosen: A.**

## API endpoints (new, under existing `auth:sanctum` + `abilities:zettly:cli`)

All under `/api/v1/...`, mirroring existing CLI routes:

- `POST /api/v1/agent/sessions` — upsert by `session_id` (idempotent)
- `POST /api/v1/agent/sessions/{sessionId}/events` — append (dedup by event_key)
- `GET  /api/v1/agent/sessions?since=...` — list
- `POST /api/v1/journal/entries` — append manual entry
- `GET  /api/v1/journal/entries?date=...` — list
- `POST /api/v1/reports/generate` — trigger report generation for due periods
- `POST /api/v1/reports/deliver` — enqueue delivery of generated reports
- `GET  /api/v1/reports?period_kind=...&date=...` — read
- `POST /api/v1/report-channels` / `GET /api/v1/report-channels` — manage webhook config

## Service / job

- `AgentSessionIngestor` (service): validates + upserts session/events, applies
  `SECRET` redaction + `category()` auto-classify (port the regex `CATS`
  list into a PHP enum/class).
- `ReportGenerator` (service): builds Markdown for a period (port of
  `render()` in the Python script).
- `DispatchReportGeneration` (queued job): runs on schedule (daily 23:55 WIB
  via `schedule:run`) — generates due reports, then dispatches delivery.
- `DeliverReport` (queued job, with retries/backoff): POSTs to configured
  webhook, updates `report_deliveries`.

## Codex hook change (`codex_journal.py`)

- Replace `open_db`/SQLite with an HTTP client that POSTs to Zettly
  `/api/v1/agent/sessions` + `/events`, using a Sanctum CLI token read from
  env (`ZETTLY_API_BASE`, `ZETTLY_CLI_TOKEN`).
- Keep the same dedup formula, redaction, category, and changed-files
  collection (unchanged logic).
- Add an offline retry spool: if the POST fails, append to a local
  outbox file and retry on the next hook invocation (so a lost network does
  not drop the record). This is the only new behavior.
- The report-generation + webhook-send code path moves to Zettly (Laravel
  job) and is removed from the hook (hook only ingests now).

## Scheduler & queue wiring

Zettly currently has no scheduler configured. The build must add:

- `routes/console.php` (or a dedicated `app/Console/Kernel.php` on older Laravel,
  but Laravel 12 uses `routes/console.php` via `Schedule` facade):
  register `DispatchReportGeneration` to run daily at 23:55 WIB, and
  `DispatchReportDelivery` to run every 15 minutes (or on demand after
  generation).
- Deployment step: ensure `php artisan schedule:run` is invoked every minute
  by the host OS cron (or the platform's scheduler). No new infra is needed
  beyond the cron entry; the app already uses the `database` queue driver
  (confirmed in `config/queue.php` / `.env`).
- `DeliverReport` job must be idempotent and retry-safe: re-reading
  `report_deliveries` with `status != 'delivered'` and not re-enqueueing
  already-delivered rows.

## ACTIVE.md -> Todo field mapping

The `journal:import-legacy` command (and any future manual import of
`activity/ACTIVE.md`) maps rows into existing `Todo` records with:

- `type = 'todo'`
- `title` ← `goal` column from `ACTIVE.md`
- `description` ← `next action` column
- `due_date` ← `Updated (WIB)` (or the date column if present; otherwise
  null)
- `priority` ← derived from `status`: `in_progress` → `urgent`, `blocked` →
  `urgent`, `open` → `not_urgent`, `done` → `not_urgent`
- `importance` ← default `not_important` unless `status = 'blocked'` →
  `important`
- `tags` ← `branch` value (e.g. `main`, `feature/x`) **plus** a fixed tag
  `@journal` so all imported active tasks group under one board column.
- `is_completed` ← `true` when `status = 'done'`, `false` otherwise.
- `organization_id` ← null (personal, not org-scoped), matching how the
  owner's manual todos are created today.

No dedicated Zettly board view is required in this phase; the `@journal` tag
is enough to filter/group in the existing Todo list UI.

## Migration of historical data (one-time)

- A PHP artisan command (`journal:import-legacy --db <path> --journal-root <path>`)
  reads the existing `events.sqlite3` (`tasks`, `events`, `reports`) and the
  `activity/daily/YYYY/MM/*.md` files, and upserts them into
  `agent_sessions`/`agent_events`/`reports`/`journal_entries` **for the
  owner's Zettly user account** (the user who owns the Zettly instance;
  identified by the `--user-id` flag, defaulting to the first/owner user).
  `ACTIVE.md` rows are imported as `Todo` records per the mapping above.
  Idempotent (dedup keys already exist; re-runs skip already-present keys).
- After import, the old journal repo becomes read-only/retired (keep as
  archive, do not delete immediately).

## What's left to the builder

- The exact Zettly owner `user_id` to pass to `--user-id` on
  `journal:import-legacy`; default to the first registered user (the
  Zettly owner) and document that clearly.
- Whether to also import `TEMPLATE.md`-derived fields that are not captured
  by `ACTIVE.md` (e.g. "Decisions" free-text) — treat as out of scope for
  v1 unless the owner explicitly requests it.
